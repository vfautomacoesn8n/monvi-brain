# Monvi Core Brain

Fundação técnica do Monvi Core Brain MVP, autorizada pela Task 041 e evoluída pelas Tasks 043 (persistência), 044 (identidade/autenticação/autorização), 045 (correção e validação factual), 053 a 062 (Fase 5 — API operacional de clientes, projetos, contatos, participação em projetos, tarefas, entregáveis, aprovações, dependências, riscos, comentários, histórico de mudanças e dashboard de projeto — os 12 entregáveis da fase, completos), 065, 066, 067 e 068 (Fase 6 — `lead`, `opportunity`, `activity` e dashboard de indicadores comerciais), 069, 070, 071, 072, 073, 074 e 075 (Fase 7 — `source`, `document`/`document_version`, classificação, permissões granulares, política de retenção, busca textual e memória operacional, camada de conhecimento), 076, 077, 078, 079 e 080 (Fase 8 — `automation_workflow`, `automation_trigger` e `automation_invocation`, catálogo, gatilhos/webhooks reais, fila/retries/idempotência/dead-letter, aprovações/reprocessamento e logs/métricas de automação), 081, 082 e 083 (Fase 9 — `ai_agent`, catálogo de agentes de IA, políticas/limites operacionais e sinalização de aprovação humana, pausada por decisão do CEO até haver decisão sobre execução real de agentes) e 084 e 085 (Fase 10 — `integration`, catálogo de integrações externas e primeira chamada real de saída ao GitHub).

## Escopo implementado

- TypeScript e Fastify;
- configuração validada com Zod;
- logs estruturados;
- tratamento básico de erros;
- `GET /api/v1/health`;
- `GET /api/v1/ready`;
- schema de domínio via Drizzle (pessoa, identidade, perfil, papel, permissão, cliente, projeto, tarefa, entregável, aprovação, dependência, risco, comentário, lead, oportunidade, atividade, fonte de conhecimento, documento, versão de documento, permissão de documento, nota de memória operacional, workflow de automação, gatilho de automação, invocação de automação, agente de IA, integração externa, sessão);
- persistência local via PostgreSQL e migrações Drizzle (Fase 3);
- autenticação de desenvolvimento (`POST /api/v1/auth/dev-login`, bloqueada quando `NODE_ENV=production`) e autorização RBAC (Fase 4);
- API operacional de clientes, projetos, contatos, participação em projetos, tarefas, entregáveis, aprovações, dependências entre tarefas, riscos e comentários em tarefas (CRUD/gestão de ciclo de vida, com autenticação e RBAC obrigatórios), sob suposição explícita de single-tenant — sem modelo de multi-organização, decisão ainda pendente (Fase 5, Tasks 053 a 062);
- API de leitura do histórico de mudanças (`GET /api/v1/history`), genérica para todas as entidades da Fase 5, reaproveitando a tabela `audit_event` já existente desde a Fase 4 — nenhuma tabela nova criada;
- dashboard operacional mínimo por projeto (`GET /api/v1/projects/:projectId/dashboard`), agregando contagens reais de tarefas, entregáveis, riscos e aprovações por status (e riscos por severidade) — também sem tabela nova, apenas `COUNT(*) GROUP BY status` sobre as tabelas já existentes;
- API operacional de leads (`GET/POST/PATCH/DELETE /api/v1/leads`), primeira entidade da Fase 6 — origem, status e responsável comercial opcional, sob a mesma suposição single-tenant;
- API operacional de oportunidades (`GET/POST/PATCH/DELETE /api/v1/opportunities`), segunda entidade da Fase 6 — origem opcional em `lead`, estágio de funil, motivo de perda e responsável comercial opcional;
- API operacional de atividades (`GET/POST/PATCH/DELETE /api/v1/activities`), terceira entidade da Fase 6 — unifica diagnóstico, proposta e follow-up num único tipo com discriminador (`activity_type`), vinculada a `lead` e/ou `opportunity`;
- dashboard de indicadores comerciais (`GET /api/v1/commercial/dashboard`), agregando contagens reais de leads por status, oportunidades por estágio e atividades por status e por tipo — também sem tabela nova, apenas `COUNT(*) GROUP BY` sobre `lead`, `opportunity` e `activity`;
- API operacional de fontes de conhecimento (`GET/POST/PATCH/DELETE /api/v1/sources`), primeira entidade da Fase 7 — nome, tipo (`manual`/`upload`/`google_drive`/`website`/`api`/`other`), descrição, responsável e status (`active`/`archived`) opcionais, pré-requisito para documentos, permissões e indexação da fase;
- API operacional de documentos e versões (`GET/POST/PATCH/DELETE /api/v1/documents`, `GET/POST /api/v1/documents/:documentId/versions`), segunda entidade da Fase 7 — `document` com título, origem opcional em `source`, responsável, status (`draft`/`review`/`approved`/`deprecated`/`archived`) e confidencialidade (`public`/`internal`/`confidential`/`restricted`) opcionais; `document_version` imutável (sem `PATCH`/`DELETE`), com número de versão auto-incremental por documento e conteúdo textual;
- classificação de documentos (Task 071, terceiro entregável da Fase 7) — `document.confidentiality` reaproveita exatamente o vocabulário canônico já definido em [`KNOWLEDGE-MODEL.md`](../../00_SYSTEM/canonical/KNOWLEDGE-MODEL.md) (`public`/`internal`/`confidential`/`restricted`); `document.status` foi realinhado ao `Status` canônico do mesmo documento (`draft`/`review`/`approved`/`deprecated`/`archived`, antes `draft`/`published`/`archived`);
- permissões granulares por documento (`POST/GET /api/v1/documents/:documentId/permissions`, `DELETE /api/v1/permissions/:id`, Task 072, quarto entregável da Fase 7) — `document_permission` concede acesso (`read`/`write`) a uma pessoa **ou** a um papel (exatamente um dos dois) sobre um documento específico; documentos `public`/`internal` continuam com o comportamento de antes (só RBAC global); documentos `confidential`/`restricted` agora exigem, além do RBAC global, uma concessão explícita — quem não tem `admin` nem concessão recebe 403 em `GET/PATCH/DELETE /documents/:id`, e `GET /documents` filtra da listagem os documentos restritos sem concessão;
- política de retenção de documentos (Task 073, último pré-requisito bloqueante da regra da Fase 7 antes de embeddings) — `document.retentionPolicy` (`indefinite`, padrão, ou `time_limited`) e `document.retentionUntil` (data, obrigatória quando `time_limited`, proibida quando `indefinite`, validado no mesmo pedido); **puramente declarativo nesta versão** — nenhum job descarta ou arquiva automaticamente documentos vencidos, isso depende da Fase 8 (Plataforma de automações), ainda não iniciada;
- indexação e busca textual (`GET /api/v1/search?q=<termo>`, Task 074, entregáveis "indexação"/"busca textual" da Fase 7, combinados numa fatia por serem inseparáveis na prática) — busca por relevância (`ts_rank`) sobre o título do documento e o conteúdo da versão mais recente, usando `to_tsvector`/`plainto_tsquery` do próprio Postgres (idioma `portuguese`), sem nenhuma dependência de software nova; respeita a mesma checagem granular de `document_permission` já usada em `GET /documents` — resultados de documentos `confidential`/`restricted` sem concessão são omitidos, não geram erro; **não indexa arquivos nem faz extração de conteúdo binário** — "extração" real (upload de arquivo, parsing de PDF/Word etc.) segue fora de escopo, deliberadamente adiada até haver uma decisão de infraestrutura de armazenamento de arquivos;
- memória operacional (`GET/POST/PATCH/DELETE /api/v1/memory-notes`, Task 075, penúltimo entregável da Fase 7) — `memory_note`: anotações leves e de curto prazo (contexto operacional, lembretes), distintas de `document` (formal, versionado, classificado); referência genérica opcional a qualquer entidade via `entityType`/`entityId` (texto livre + UUID, sem FK — mesmo padrão de referência polimórfica já usado em `audit_event`/`GET /history`, já que uma nota pode se referir a `lead`, `client`, `project`, `document` etc.), autor automático (`request.user.personId`), `expiresAt` opcional (memória operacional pode ser efêmera; `null` = permanece indefinidamente); `GET /memory-notes` aceita filtro opcional por `entityType`/`entityId`; **sem permissão granular por nota** — RBAC global (`memory:read`/`write`) apenas, já que a permissão granular foi construída especificamente para `document` (Task 072) e não generalizada aqui sem necessidade real demonstrada;
- API operacional de workflows de automação (`GET/POST/PATCH/DELETE /api/v1/automation-workflows`, Task 076, primeira entidade da Fase 8) — `automation_workflow`: nome, descrição, responsável e tipo de gatilho pretendido (`trigger_type`: `manual`/`webhook`/`schedule`/`event`) opcionais, status (`draft`/`active`/`paused`/`archived`, padrão `draft`); **puramente cadastro nesta versão** — `triggerType` só descreve a intenção de disparo, nenhum gatilho real dispara nada ainda; execução, filas, retries, idempotência e dead-letter são entregáveis seguintes da mesma fase;
- gatilhos e webhooks reais (Task 077, segundo e terceiro entregáveis da Fase 8, combinados numa fatia) — `automation_trigger` (`POST/GET /api/v1/automation-workflows/:workflowId/triggers`, `GET/PATCH/DELETE /api/v1/automation-triggers/:id`) configura como um workflow é disparado; quando `triggerType` é `webhook`, um `webhookToken` aleatório (32 bytes, hex) é gerado automaticamente; `scheduleCron`/`eventName` são armazenados quando aplicável, mas **não executados** — nenhum agendador ou consumidor de eventos real existe ainda. `POST /api/v1/automation-triggers/:token/invoke` é a única rota **pública** (sem `Authorization`) de todo o sistema — decisão deliberada: sistemas externos reais (n8n, GitHub etc.) não conseguem autenticar com Bearer token da Monvi, então o segredo é o próprio `webhookToken` no caminho da URL, validado contra um gatilho ativo do tipo `webhook`;
- fila, retries, idempotência e dead-letter (Task 078, quarto a sétimo entregáveis da Fase 8, combinados por girarem em torno do mesmo ciclo de vida de `automation_invocation`) — `POST /automation-triggers/:token/invoke` aceita `idempotencyKey` opcional no corpo; uma segunda chamada com a mesma chave para o mesmo gatilho retorna a invocação já existente (`200`, `deduplicated: true`) em vez de criar duplicata. Cada invocação nasce com `status: pending`, `attemptCount: 0` e `maxAttempts: 3`; `GET /api/v1/automation-invocations/queue` (autenticado) lista as invocações pendentes prontas para processar (`nextAttemptAt` vencido ou nulo) — é a fila real, consultável via API, sem nenhum serviço de fila externo. `POST /api/v1/automation-invocations/:id/attempt` (autenticado) registra o resultado de uma tentativa; sucesso encerra (`succeeded`); falha incrementa `attemptCount` e agenda a próxima tentativa com backoff exponencial (`2^attemptCount` minutos), ou vira `dead_letter` ao esgotar `maxAttempts`; tentar uma invocação fora de `pending` retorna `409`. **Continua sem nenhum worker real** consumindo a fila automaticamente — quem chama `/attempt` ainda é manual ou externo (ex.: futuramente n8n);
- aprovações e reprocessamento (Task 079, oitavo e décimo entregáveis da Fase 8) — `automation_workflow.requiresApproval` (booleano, padrão `false`): quando `true`, uma invocação recebida via `/invoke` nasce `pending_approval` em vez de `pending` e **não aparece na fila** nem aceita `/attempt` até ser decidida. `POST /automation-invocations/:id/approve` (autenticado, `{ approved, reason? }`) decide: aprovado vira `pending` (entra na fila normalmente); rejeitado vira `rejected` (estado terminal, com `rejectionReason` registrado); só aceita invocações `pending_approval`, senão `409`. `POST /automation-invocations/:id/reprocess` (autenticado) só para invocações `dead_letter` — reseta `attemptCount` para `0`, limpa `lastError`/`nextAttemptAt` e volta para `pending`, dando uma segunda chance sem precisar de um novo webhook; fora de `dead_letter`, `409`. Reaproveita `automationInvocationStatusEnum` (sem tabela nova) e o campo `approvedByPersonId` para registrar quem decidiu — mesmo padrão de auditoria de decisão já usado em `approval` (Fase 5), sem reaproveitar aquela tabela (que é fixa a `deliverable` por FK);
- logs e métricas de automação (Task 080, décimo e décimo-primeiro entregáveis da Fase 8) — "logs": `GET /api/v1/history` (Task 061) ganhou uma entrada nova em seu mapa de entidades (`automation_invocation` → prefixo `automation_invocation:`, chave `automationInvocationId`), então `GET /history?entityType=automation_invocation&entityId=<uuid>` já retorna o histórico real de uma invocação (`received`/`attempted`/`approval_decided`/`reprocessed`) — nenhuma rota nova, nenhuma tabela nova, só uma linha de configuração no endpoint genérico já existente; "métricas": `GET /api/v1/automations/dashboard` (arquivo novo, mesmo padrão dos dashboards de projeto e comercial) agrega contagens reais de `automation_workflow` por status e `automation_invocation` por status — também sem tabela nova, apenas `COUNT(*) GROUP BY status`;
- API operacional de agentes de IA (`GET/POST/PATCH/DELETE /api/v1/ai-agents`, Task 081, primeira entidade da Fase 9) — `ai_agent`: nome, descrição, propósito (texto livre), ferramentas permitidas (`allowedTools`, lista de strings), fontes autorizadas (`authorizedSourceIds`, lista opcional de UUIDs referenciando `source` da Fase 7, sem FK), responsável e status (`draft`/`active`/`paused`/`archived`, padrão `draft`) opcionais; **puramente cadastro nesta versão** — nenhum agente é de fato invocado, nenhuma ferramenta listada é de fato chamada; políticas, limites, aprovações humanas, avaliações, métricas de qualidade, fallback, controle de custo e proteção contra prompt injection são entregáveis seguintes da mesma fase, deliberadamente anteriores a qualquer execução real de agente;
- políticas e limites de agentes de IA (Task 082, quinto e sexto entregáveis da Fase 9) — `ai_agent.policy` (texto livre, regras de comportamento que o agente deve seguir), `maxActionsPerRun` e `timeoutSeconds` (inteiros opcionais, limites operacionais básicos); **também puramente declarativo** — como não existe nenhuma capacidade de execução de agente ainda, não há nada em tempo real para aplicar essas regras contra; controle de custo fica deliberadamente fora (entregável próprio, mais adiante na fase);
- sinalização de aprovação humana (Task 083, sétimo entregável da Fase 9) — `ai_agent.requiresHumanApproval` (booleano, padrão `false`); mesmo padrão declarativo das duas fatias anteriores, já que ainda não existe nenhuma execução real de agente para exigir aprovação antes de rodar — quando essa execução existir, este campo já estará pronto para ser consultado;
- API operacional de integrações externas (`GET/POST/PATCH/DELETE /api/v1/integrations`, Task 084, primeiro entregável da Fase 10) — `integration`: provedor (`github`/`google_workspace`/`forms_email`/`whatsapp`/`crm_spreadsheets`/`n8n`/`nuvemshop`/`analytics_media`/`other`), nome, escopos mínimos pretendidos (texto livre), responsável e status (`draft`/`active`/`paused`/`revoked`, padrão `draft`) opcionais; **puramente cadastro nesta versão** — nenhuma credencial real é armazenada, nenhuma chamada real a API externa é feita, nenhum webhook real existe; os dez entregáveis restantes por integração (credenciais segregadas, escopos mínimos aplicados, webhook seguro, retry, idempotência, logs, monitoramento, revogação, documentação, teste de falha) dependem de decisão do CEO sobre qual serviço externo real conectar primeiro, e de credenciais reais que só ele pode fornecer;
- primeira integração de saída real do projeto: GitHub (`GET /api/v1/integrations/:id/github/repository?owner=<owner>&repo=<repo>`, Task 085) — busca informações públicas de um repositório (nome, branch padrão, contagem de issues abertas, URL) via `GET /repos/{owner}/{repo}` da API real do GitHub, autenticado com um Personal Access Token lido de `GITHUB_PAT` (variável de ambiente, nunca armazenado em banco, nunca logado); exige que a integração referenciada tenha `provider: github` (400 caso contrário); retorna `424` se `GITHUB_PAT` não estiver configurado, `502` se o próprio GitHub retornar erro; toda chamada (sucesso ou falha) gera um `audit_event`, sem o token. **Primeira chamada real de saída a um serviço externo em todo o projeto** — usa `fetch` nativo do Node (sem dependência nova), sem retry além de uma tentativa extra em falha de rede transitória, sem escrita (só leitura), escopo deliberadamente mínimo;
- testes automatizados unitários, de configuração, de autenticação/autorização e de rotas de clientes, projetos, contatos, participação em projetos, tarefas, entregáveis, aprovações, dependências, riscos, comentários, histórico de mudanças, dashboard, leads, oportunidades, atividades, indicadores comerciais, fontes de conhecimento, documentos/versões, permissões de documento, busca textual, memória operacional, workflows de automação, gatilhos/webhooks, fila/retries/idempotência/dead-letter, aprovações/reprocessamento, logs/métricas de automação, agentes de IA e integrações externas (catálogo e chamada real ao GitHub).

Autenticação de produção real (Google Workspace/OIDC), modelo de multi-organização, dados reais de clientes, homologação e produção permanecem fora do escopo. A Fase 10 (integrações externas) é a primeira exceção à ausência de credenciais reais no projeto — ver detalhes abaixo. Os 12 entregáveis previstos para a Fase 5 no Plano Mestre estão implementados; falta a Parte B (validação real contra Postgres, deliberadamente adiada) e a decisão de multi-organização. Comentários estão escopados a tarefas apenas; o dashboard de projeto cobre tarefas, entregáveis, riscos e aprovações. Da Fase 6 (comercial e CRM), `lead`, `opportunity`, `activity` e o dashboard de indicadores comerciais estão implementados — "qualificação" foi considerada já coberta por `lead.status`/`notes`, sem entidade própria; falta apenas integrações externas. Da Fase 7 (conhecimento, documentos e memória), `source`, `document`/`document_version`, classificação, permissões, política de retenção, busca textual e memória operacional estão implementados — apenas extração de arquivos reais falta como entregável explícito da fase; embeddings e busca vetorial já estão desbloqueados pela regra da fase, mas ainda não implementados. Da Fase 8 (plataforma de automações), catálogo, gatilhos, webhooks, fila, retries, idempotência, dead-letter, aprovações, reprocessamento, logs e métricas estão implementados — falta apenas integração com n8n, deliberadamente pendente. Da Fase 9 (agentes de IA), o catálogo, políticas/limites e a sinalização de aprovação humana (`ai_agent`, primeiro a sétimo entregáveis) estão implementados — nenhum agente executa nada de verdade nesta versão. O CEO decidiu pausar a Fase 9 nesse ponto (avaliações, métricas de qualidade, fallback, controle de custo e proteção contra prompt injection ficam pendentes) até que exista uma decisão explícita sobre execução real de agentes, e avançar para a Fase 10. Da Fase 10 (integrações externas), o catálogo (`integration`, Task 084) e a primeira chamada real de saída ao GitHub (Task 085, leitura de repositório) estão implementados — ainda sem escrita, sem webhook de entrada (exige deploy, Fases 11/12, ainda não alcançadas) e sem retry/idempotência/monitoramento dedicados; a credencial (`GITHUB_PAT`) é lida de variável de ambiente, nunca armazenada em banco. Os demais entregáveis, para GitHub ou qualquer outro provedor, dependem de decisão do CEO sobre o que conectar em seguida.

## Execução local

```powershell
npm install
npm run check
npm run dev
```

O servidor usa `127.0.0.1:3000` por padrão.

`GITHUB_PAT` (opcional): Personal Access Token do GitHub, necessário apenas para `GET /integrations/:id/github/repository` (Task 085) funcionar de verdade. Sem essa variável, a rota responde `424` de forma limpa — o servidor sobe normalmente sem ela. Recomendação de escopo: token fine-grained, permissão "Contents: Read-only", restrito ao(s) repositório(s) necessário(s). Definir como variável de ambiente do processo (`$env:GITHUB_PAT = "..."` no PowerShell) — nunca commitado, nunca passado em texto na conversa com o Helpper.

O `PATCH` de aprovação que define `status` diferente de `pending` preenche `decidedAt` automaticamente. O `POST` de dependência rejeita com 400 uma tarefa que dependa de si mesma. O autor de um comentário é sempre o usuário autenticado (`request.user.personId`), nunca informado no corpo da requisição. `GET /history` aceita `entityType` em `client`, `project`, `contact`, `project_membership`, `task`, `deliverable`, `approval`, `dependency`, `risk`, `comment` ou `automation_invocation` (Task 080), e retorna os eventos de `audit_event` daquela entidade, mais recentes primeiro — não é uma tabela nova, é leitura sobre a auditoria já gravada por cada rota desde a Fase 4. `GET /projects/:projectId/dashboard` retorna contagens de tarefas e entregáveis por status, riscos por status e severidade, e aprovações por status (agregadas via `deliverable` do projeto) — todos os status possíveis aparecem com valor `0` quando não há registros, sem tabela nova. `lead` não referencia `client` — representa um contato ainda não convertido, com seus próprios dados (nome, empresa, e-mail, telefone), origem (`source`) e status de funil (`new`/`contacted`/`qualified`/`disqualified`/`converted`). `opportunity` referencia `lead` de forma opcional (`leadId`, `onDelete: set null`) e tem seu próprio estágio de funil (`opportunity_stage`: `prospecting`/`qualification`/`proposal`/`negotiation`/`won`/`lost`) e `lossReason`, preenchido livremente quando o estágio vira `lost` — sem validação de obrigatoriedade nesta primeira versão. `activity` unifica diagnóstico, proposta e follow-up (e outros tipos de interação: `call`, `meeting`, `other`) num único tipo com discriminador (`activity_type`); o `POST` exige que a atividade esteja vinculada a pelo menos um `leadId` ou `opportunityId`, rejeitando com 400 quando nenhum dos dois é informado; `GET /activities` aceita filtros opcionais `leadId`/`opportunityId` na query string. `GET /commercial/dashboard` retorna contagens globais (não escopadas a projeto) de leads por status, oportunidades por estágio e atividades por status e por tipo — todos os valores possíveis dos enums aparecem com `0` quando não há registros, sem tabela nova, mesmo padrão do dashboard de projeto. `source` (primeira entidade da Fase 7) representa de onde vem o conhecimento institucional — documento manual, upload, Google Drive, site, API ou outro (`source_type`) — com status próprio (`source_status`: `active`/`archived`); é um cadastro isolado, sem relação com nenhuma entidade das Fases 5/6, e existe como pré-requisito documentado no Plano Mestre antes de `document`, permissões e indexação poderem ser construídos. `document` (segunda entidade da Fase 7) referencia `source` de forma opcional (`sourceId`, `onDelete: set null`) e tem status próprio (`document_status`: `draft`/`review`/`approved`/`deprecated`/`archived`, realinhado na Task 071 ao `Status` canônico de `KNOWLEDGE-MODEL.md`); `document_version` é imutável — cada `POST /documents/:documentId/versions` cria uma nova linha com `versionNumber` calculado automaticamente (`max(versionNumber) + 1` por documento, com índice único garantindo não haver dois registros com o mesmo número para o mesmo documento) e não existe rota de edição ou remoção de versão. `document.confidentiality` (`public`/`internal`/`confidential`/`restricted`, Task 071) reaproveita exatamente o vocabulário canônico de confidencialidade já definido em `KNOWLEDGE-MODEL.md`, usado em todo o resto do sistema (frontmatter de tasks, páginas da Wiki). `document_permission` (Task 072) torna essa classificação efetiva: para documentos `public`/`internal`, nada muda — basta a permissão global (`document:read`/`write`); para `confidential`/`restricted`, o usuário precisa ser `admin` (mesmo bypass já usado em todo o RBAC) ou ter uma concessão explícita — via `granteePersonId` (uma pessoa específica) ou `granteeRoleId` (qualquer pessoa daquele papel), nunca os dois nem nenhum no mesmo registro — com `accessLevel` `read` (permite leitura) ou `write` (permite leitura e escrita). `GET /documents` omite silenciosamente os documentos restritos sem concessão (não retorna erro, apenas não lista); `GET/PATCH/DELETE /documents/:id` retornam 403 quando o documento é restrito e não há concessão. Revogar uma concessão é exclusão lógica (`DELETE /permissions/:id`), sem rota de edição — para trocar o nível de acesso, revoga-se e concede-se de novo. `document.retentionPolicy`/`retentionUntil` (Task 073) registram a política de retenção — `indefinite` (padrão) não tem `retentionUntil`; `time_limited` exige `retentionUntil` no mesmo pedido (`POST`/`PATCH`), rejeitando com 400 qualquer combinação inconsistente (política sem data compatível, ou data sem `time_limited`). É puramente declarativo: nenhuma rota ou processo descarta, arquiva ou notifica automaticamente quando `retentionUntil` vence — isso depende de execução recorrente agendada, que é território da Fase 8 (Plataforma de automações), ainda não iniciada. `GET /search?q=<termo>` (Task 074) busca por relevância (`ts_rank`) no título do documento e no conteúdo da versão mais recente (`document_version` com maior `versionNumber`), usando `to_tsvector`/`plainto_tsquery` nativos do Postgres (idioma `portuguese`) — sem nenhuma tabela, coluna ou dependência de software nova; a checagem de acesso reaproveita exatamente `hasGranularDocumentAccess` (extraída para `src/modules/documents/access.service.ts` nesta task, para ser compartilhada entre `document.ts` e `search.ts`), então resultados de documentos `confidential`/`restricted` sem concessão explícita simplesmente não aparecem, sem gerar erro. Limitação deliberada: a busca calcula o `tsvector` em tempo de consulta a cada requisição, sem nenhuma coluna ou índice persistido (GIN) — aceitável no volume atual e enquanto a Parte B (única forma de medir desempenho real) seguir adiada; otimizar isso é trabalho futuro, não antecipado sem evidência real de necessidade. Só busca em texto já armazenado como `document_version.content` — não faz upload, parsing nem extração de conteúdo de arquivos binários (PDF, Word etc.), que é uma frente de infraestrutura própria, deliberadamente fora de escopo até haver uma decisão sobre armazenamento de arquivos. `memory_note` (Task 075) é intencionalmente mais simples que `document`: sem versionamento, sem classificação, sem permissão granular — pensada para contexto operacional de curto prazo (ex.: "lead pediu para só ser contatado depois das 14h"), não para conhecimento institucional formal. `entityType`/`entityId` são uma referência genérica sem FK (mesmo padrão de `audit_event`), então nada impede referenciar um `entityId` que não existe mais — decisão deliberada de simplicidade, já que memória operacional não precisa da mesma integridade referencial que os relacionamentos formais do sistema. `expiresAt` é só um campo informativo nesta versão: nada expira ou é removido automaticamente quando a data passa, assim como `document.retentionUntil` (Task 073) — qualquer expiração automática real dependeria da Fase 8. `automation_workflow` (Task 076, primeira entidade da Fase 8) é o catálogo de workflows — `triggerType` (`manual`/`webhook`/`schedule`/`event`) descreve apenas a intenção de como o workflow deveria ser disparado; nenhum gatilho real dispara nada nesta versão, é puro cadastro. `status` (`draft`/`active`/`paused`/`archived`) também não afeta nenhum comportamento de execução ainda — é só metadado, já que execução em si (filas, retries, idempotência, dead-letter) é entregável futuro da mesma fase. `automation_trigger` (Task 077) referencia um `automation_workflow` (`onDelete: cascade`) e configura como ele deveria ser disparado; quando `triggerType` é `webhook`, `webhookToken` é gerado automaticamente (32 bytes aleatórios em hex) — é o único jeito de disparar algo de verdade nesta fase. `scheduleCron`/`eventName` são armazenados para os tipos `schedule`/`event`, mas continuam sem nenhuma execução real (não há agendador nem consumidor de eventos). `POST /automation-triggers/:token/invoke` é **a única rota pública de todo o sistema** — não passa por `authenticateRequest` nem `requirePermission`, porque um webhook de verdade (n8n, GitHub, um formulário externo) não tem como autenticar com Bearer token da Monvi; a segurança é o próprio `webhookToken` no caminho, validado contra um gatilho ativo do tipo `webhook` (404 se não encontrar). Cada chamada bem-sucedida cria um `automation_invocation` — payload recebido, IP de origem, data, mais o estado de processamento descrito abaixo (Task 078) — e retorna `202 Accepted` (recebido; "processado" depende de alguém chamar `/attempt`). `GET /automation-triggers/:id/invocations` (autenticado) lista o histórico de chamadas recebidas por um gatilho. `idempotencyKey` (Task 078, opcional no corpo de `/invoke`) evita duplicidade: uma segunda chamada com a mesma chave para o mesmo gatilho não cria uma nova invocação — retorna a existente com `200` e `deduplicated: true` em vez de `202`. Toda invocação nasce `status: pending`, `attemptCount: 0`, `maxAttempts: 3`. `GET /automation-invocations/queue` (autenticado) é a fila de verdade — lista invocações `pending` cujo `nextAttemptAt` já venceu ou nunca foi definido, ordenadas por `receivedAt` — sem nenhum serviço de fila externo, é só uma consulta SQL. `POST /automation-invocations/:id/attempt` (autenticado, corpo `{ success, error? }`) registra o resultado: sucesso muda para `succeeded` (estado terminal); falha incrementa `attemptCount` e agenda a próxima tentativa com backoff exponencial (`2^attemptCount` minutos) até `maxAttempts`, quando então vira `dead_letter` (também terminal). Chamar `/attempt` numa invocação fora de `pending` retorna `409` — evita processar algo em estado errado. Nada aqui consome a fila automaticamente: `/attempt` continua sendo chamado manualmente ou por um sistema externo (ex.: n8n, quando essa integração existir); não há worker, cron nem processo em background real. `automation_workflow.requiresApproval` (Task 079) muda o estado inicial de uma invocação: se `true`, `/invoke` cria a invocação como `pending_approval` em vez de `pending` — ela não aparece em `/queue` nem aceita `/attempt` até ser decidida. `POST /automation-invocations/:id/approve` (`{ approved, reason? }`) decide: aprovado vira `pending` (agora sim entra na fila); rejeitado vira `rejected`, estado terminal, com `rejectionReason` registrado; só aceita invocações `pending_approval`, senão `409`. `POST /automation-invocations/:id/reprocess` dá uma segunda chance a uma invocação `dead_letter` — reseta `attemptCount` para `0`, limpa `lastError`/`nextAttemptAt`, volta para `pending`, sem precisar de um novo webhook; fora de `dead_letter`, `409`. `approvedByPersonId`/`approvedAt` registram quem decidiu e quando, para as duas invocações (aprovada ou rejeitada). Logs e métricas de automação (Task 080) não criaram nenhuma tabela: "logs" reaproveita `GET /history` (Task 061), que já era genérico — bastou adicionar `automation_invocation` ao seu mapa interno de prefixos de `audit_event`, então `GET /history?entityType=automation_invocation&entityId=<uuid>` já retorna os quatro tipos de evento (`received`/`attempted`/`approval_decided`/`reprocessed`) de uma invocação específica. "Métricas" é `GET /automations/dashboard`, seguindo exatamente o padrão dos dois dashboards anteriores (`GET /projects/:projectId/dashboard`, Task 062; `GET /commercial/dashboard`, Task 068) — `COUNT(*) GROUP BY status` sobre `automation_workflow` e sobre `automation_invocation`, com todos os valores possíveis do enum aparecendo com `0` quando não há registros. Fica de fora desta task o último entregável da fase, integração com n8n e APIs — decisão de infraestrutura externa real, do mesmo tipo das integrações da Fase 6, deliberadamente adiada. `ai_agent` (Task 081, primeira entidade da Fase 9) segue o mesmo padrão de cadastro puro que abriu a Fase 8 (`automation_workflow`, Task 076): `purpose` descreve para que o agente serve, `allowedTools` é uma lista livre de strings com as ferramentas que o agente poderia usar (não existe ainda um catálogo formal de ferramentas no sistema, então fica texto livre), `authorizedSourceIds` é uma lista opcional de UUIDs referenciando `source` (Fase 7) sem integridade referencial forçada — mesmo padrão de referência sem FK já usado em `memory_note` (Task 075) — e `status` (`draft`/`active`/`paused`/`archived`) é só metadado. **Nada aqui invoca um agente de verdade**: não há execução de IA, não há chamada real a nenhuma ferramenta listada em `allowedTools`, e não há nenhuma verificação de que `authorizedSourceIds` aponta para fontes que realmente existem. Essa limitação é deliberada — o gate de saída da Fase 9 exige "agentes avaliados em ambiente controlado e sem ações irreversíveis autônomas", e políticas, limites e aprovações humanas (entregáveis seguintes da mesma fase) precisam existir antes de qualquer execução real ser considerada seguro construir. `ai_agent.policy`/`maxActionsPerRun`/`timeoutSeconds` (Task 082) estendem a mesma entidade — `policy` é texto livre descrevendo regras de comportamento (ex.: "não enviar e-mails sem revisão humana"); `maxActionsPerRun` e `timeoutSeconds` são limites operacionais básicos, ambos inteiros opcionais. **Nenhum dos três é aplicado contra nada** — permanecem metadados até existir alguma forma real de execução de agente para checar contra eles; controle de custo foi deliberadamente deixado fora desta fatia, por ser um entregável próprio mais adiante na fase, provavelmente ligado a métricas de uso reais que também ainda não existem. `ai_agent.requiresHumanApproval` (Task 083, booleano, padrão `false`) segue a mesma disciplina: sinaliza que, quando execução real existir, esse agente vai exigir aprovação humana antes de rodar, mas **não há nenhum fluxo de aprovação real construído ainda** — nenhuma fila de pendências, nenhum endpoint de decisão. Diferente da Fase 8, onde `automation_workflow.requiresApproval` (Task 079) foi construído depois que a execução real já existia (Tasks 077/078), aqui a ordem é invertida: o campo existe antes de haver qualquer coisa real para aprovar, deliberadamente, para não repetir a construção de infraestrutura órfã. O CEO decidiu pausar a Fase 9 neste ponto e avançar para a Fase 10 (integrações externas). `integration` (Task 084, primeira entidade da Fase 10) segue o mesmo padrão de catálogo puro que abriu as Fases 8 e 9 — `provider` é um enum fechado com as nove integrações previstas na ordem recomendada do Plano Mestre (GitHub, Google Workspace, formulários/e-mail, WhatsApp, CRM/planilhas, n8n, Nuvemshop, analytics/mídia, outras), `minimalScopes` é texto livre descrevendo os escopos mínimos pretendidos. **Nada aqui se conecta a nenhum serviço externo de verdade**: nenhuma credencial é armazenada, nenhuma chamada de API externa é feita, nenhum webhook real existe. Essa é a primeira fase do projeto em que os entregáveis restantes (credenciais segregadas, webhook seguro, retry, idempotência, logs, monitoramento, revogação, documentação, teste de falha, por integração) dependem estruturalmente de decisões e credenciais reais que só o CEO pode fornecer — diferente de toda a base construída até aqui, que não dependia de nenhum serviço externo. `GET /integrations/:id/github/repository` (Task 085) é a primeira dessas decisões em execução: a direção escolhida foi saída (Monvi chamando a API real do GitHub), não entrada (webhook do GitHub chegando aqui), porque o servidor roda hoje só em `127.0.0.1` — sem URL pública, o GitHub não teria como alcançar um webhook de entrada, então essa direção fica registrada como próxima fatia, para quando houver deploy (Fases 11/12). A rota exige que a `integration` referenciada por `:id` tenha `provider: github` (`400` caso contrário), lê `GITHUB_PAT` da configuração tipada (`src/config/environment.ts`, nunca do banco), e chama `GET /repos/{owner}/{repo}` da API real do GitHub via `fetch` nativo (nenhuma dependência HTTP nova). Se `GITHUB_PAT` não estiver definido, retorna `424 Failed Dependency` de forma limpa, sem derrubar o servidor — o resto do sistema continua funcionando normalmente sem essa variável. Se o próprio GitHub responder com erro (token inválido, repositório inexistente, limite de taxa), a rota retorna `502 Bad Gateway` repassando a mensagem do GitHub. Toda chamada — sucesso, credencial ausente ou erro do GitHub — gera um `audit_event` (`integration:github_call`), mas o token em si nunca é gravado em lugar nenhum. Escopo deliberadamente mínimo: só leitura (nenhuma escrita no GitHub), sem retry sofisticado (uma única tentativa extra em falha de rede transitória), sem idempotência (não aplicável a uma chamada de leitura).

1. Subir o banco local definido em `infrastructure/local/docker-compose.yml`:

   ```powershell
   docker compose -f ../../infrastructure/local/docker-compose.yml up -d
   ```

2. Aplicar as migrações:

   ```powershell
   npm run db:migrate
   ```

3. Rodar o teste de integração real, contra o banco em execução (não mockado):

   ```powershell
   npm run test:integration
   ```
